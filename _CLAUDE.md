## Атрибуция

- **никаких следов AI-ассистента нигде.** Ни в commit-сообщениях (никаких `Co-Authored-By`), ни в описаниях MR/PR (никаких «Generated with»), ни в комментариях кода, README, ADR, именах веток
- если системный шаблон предлагает добавить подпись/трейлер — не добавлять

## Git commit-сообщения

- **никогда не мешать синтаксис PowerShell и Bash.** Here-string `@'...'@` — только PowerShell; в Bash tool он попадает в сообщение буквально (`@` первой строкой), коммит приходится переделывать
- многострочное сообщение — повторяющиеся `-m`: `git commit -m "заголовок" -m "тело"`. Работает одинаково в обеих оболочках, кавычки не ломаются
- если нужен именно heredoc — только в Bash tool и только `<<'EOF'`

## Стиль кода

- каждый атрибут JSX-элемента — на отдельной строке
- в колбэках (.map, .reduce и т.д.) использовать тело функции `{}` с `return`, деструктурировать нужные поля до `return`
- не писать inline: если выражение не помещается в одну строку — разворачивать

### JSX
Каждый проп на отдельной строке, даже если их мало:
```tsx
<LocationItem
  className="w-full h-full"
  {...item}
/>
```

### Колбэки в map/filter/reduce и подобных
Всегда явный `return` с фигурными скобками, никогда неявный возврат через `() => (...)`:
```tsx
{items.slice(0, 4).map((item, index) => {
  return (
    <div
      ref={(el) => {
        if (el) {
          itemsRef.current[index] = el;
        }
      }}
      key={index}
      className={cx(
        'd:min-w-0 d:basis-1/4',
      )}
    >
      <LocationItem
        className="w-full h-full"
        {...item}
      />
    </div>
  );
})}
```

## Стили

- в `*.module.scss` размеры пиши через `rem()`, если она есть в проекте: `font-size: rem(32)`
- значения меньше 5px — в `px` (`1px`, `2px`)
- класс, в котором только типографика (шрифт, размер, межстрочный, трекинг и т.п.), — с суффиксом `Typography`: `.phoneTypography`
- tailwind-классы, зависящие от пропа-варианта, — в `tw-classes/index.ts` компонента функциями `twClasses<Проп>(prop)` через `switch`; общие для всех вариантов классы — в базовом `cx` компонента. Если внутри варианта есть доп. условие (флаг) — ветка возвращает `cx('общие классы варианта', flag && 'классы флага')`, общие классы в тернарнике не дублировать:
```ts
export const twClassesSize = (size: ButtonSize, hasIcon: boolean): string => {
  switch (size) {
    case ButtonSize.big:
      return 'h-64 gap-12 px-24';
    case ButtonSize.def:
    default:
      return cx(
        'h-52 gap-10',
        hasIcon ? 'pl-16 pr-20' : 'px-20',
      );
  }
};
```

## Внешние сервисы (токены в env)

Значения токенов не выводить в чат, коммиты, файлы. Читать через `curl`, не WebFetch (там логин).

**Кириллица в POST/PUT** (заголовки MR, комментарии, описания) — никогда не передавать аргументами curl (`--data-urlencode "title=Привет"`, `-d '{"body":"…"}'`): на Windows shell портит кодировку, API отвечает `400 Bad Request`. Сразу так:
1. собрать payload в JSON-файл через node (пишет UTF-8): `node -e "fs.writeFileSync('p.json', JSON.stringify({title: '…', body: fs.readFileSync('text.md','utf8')}))"`; длинный текст — отдельным `.md` через Write
2. отправить файлом: `curl -s -H "Content-Type: application/json" -X POST "<url>" --data-binary "@p.json"`

Файлы payload — в scratchpad.

## Принципы разработки

### 1. Думай перед кодом

**Не предполагай молча. Выявляй трейдоффы.**

Перед реализацией:
- явно называй допущения; если не уверен — спроси
- если возможны несколько трактовок — перечисли, не выбирай молча
- если есть более простой подход — скажи, предложи
- если что-то непонятно — останови, назови что именно, спроси

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- никаких фич сверх запрошенного
- никаких абстракций для единственного использования
- никакой «гибкости» или «конфигурируемости» без запроса
- никакой обработки ошибок для невозможных сценариев
- если написал 200 строк, а можно 50 — перепиши

Спроси себя: «Скажет ли senior-инженер, что это overcomplicated?» Если да — упрости.

### 3. Хирургические изменения

**Трогай только то, что необходимо. Убирай только свой мусор.**

При редактировании существующего кода:
- не «улучшай» соседний код, комментарии, форматирование
- не рефакторь то, что не сломано
- соответствуй существующему стилю, даже если ты бы сделал иначе
- заметил мёртвый код — упомяни, не удаляй

После своих изменений:
- удаляй импорты/переменные/функции, осиротевшие из-за твоих правок
- не трогай pre-existing мёртвый код без запроса

Критерий: каждая изменённая строка должна прямо следовать из запроса пользователя.

### 4. Исполнение с критерием успеха

**Определяй критерий успеха. Итерируй до достижения.**

Преобразуй задачи в проверяемые цели:
- «Добавь валидацию» → «Напиши тесты для невалидных входных данных, затем сделай так, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий его, затем сделай так, чтобы он проходил»
- «Рефактор X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач — краткий план:
```
1. [Шаг] → проверка: [что проверяем]
2. [Шаг] → проверка: [что проверяем]
3. [Шаг] → проверка: [что проверяем]
```

Чёткий критерий успеха позволяет работать независимо. Размытый («сделай так, чтобы работало») требует постоянных уточнений.
