Проверяешь MR коллеги и готовишь комментарии от имени пользователя. Всё, что уходит в GitLab, сначала обсуждается в чате; отправка — только по команде «отправляй».

Доступ к GitLab — по разделу «Внешние сервисы» глобального `CLAUDE.md` (токен, `curl`, кириллица JSON-файлом). Временные файлы — в scratchpad.

## Шаги

### 1. Сверить репозиторий

Из ссылки возьми путь проекта и номер MR. Сравни с `git remote get-url origin` текущей папки. Не совпадает — остановись и спроси, где лежит локальная копия этого проекта.

### 2. Прочитать MR

Ничего не запускай, только читай:

- MR: `GET projects/<path>/merge_requests/<iid>` — ветки, описание, `diff_refs`;
- все обсуждения: `GET .../discussions?per_page=100` (листай страницы), системные заметки пропускай;
- владелец токена: `GET /user` — это «пользователь», его комментарии — «ваши»;
- `git fetch origin` и работай с `origin/<source_branch>`. Локальная ветка пользователя может отставать — сравни и скажи, на сколько коммитов.

### 3. Согласовать объём — сообщение 1

Режим:

- **полная проверка** — комментариев пользователя в MR нет: весь дифф против target по ТЗ и стандартам;
- **проверка нового** — комментарии есть: треды плюс коммиты после последнего комментария пользователя (сравни дату коммитов с `created_at` комментария).

Пришли одно сообщение:

- MR, ветки, сколько комментариев пользователя и дата последнего;
- режим;
- новые коммиты (`hash`, автор, заголовок);
- пронумерованный список тредов: статус (открыт / разрешён и кем), заголовок, автор, ответы автора MR;
- что предлагаешь проверить.

Дождись «да» или правок. Договорённостей о разрешённых тредах в команде нет, поэтому список тредов на проверку всегда утверждает пользователь.

### 4. Собрать ТЗ и стандарты

- **ТЗ** (полная проверка): из запроса пользователя; нет — из описания MR, вложений в комментариях, задачи Bitrix по номеру из имени ветки (`task_27630`). Не нашёл — спроси.
- **Стандарты**: `CLAUDE.md`, `CONTEXT.md`, `GLOSSARY.md` и доки проекта (например, `docs/guide.md`).

### 5. Проверить

Worktree в scratchpad на `origin/<source_branch>`, рабочую копию пользователя не трогай.

- Найди `package.json`, ближайший к изменениям.
- `node_modules`: если MR не менял `package.json` и lock-файл — junction на `node_modules` из рабочей копии (`cmd //c mklink /J "<wt>\...\node_modules" "<repo>\...\node_modules"`); иначе установка в worktree.
- Прогони то, что есть в скриптах: `typecheck`, `lint`, `test`, `build`.
- Каждое подозрение доводи до факта: точечная проверка под него (греп по собранному CSS, `dev`, тест). Зелёный `build` не значит, что результат верный: проверь, что в нём есть то, что должно быть.
- Каждый пункт утверждённых тредов и ТЗ — подтверждён или опровергнут фактом.
- Ищи хвосты: старые пути и упоминания после переносов, файлы вне своей папки, изменения не по запросу, ответы автора «проверил — работает» без доказательства.

Уборка: сначала сними junction (`cmd //c rmdir "<путь к junction>"` — удаляет только ссылку), потом worktree. Длинные пути `git worktree remove` не удалит — тогда `Remove-Item -LiteralPath "\\?\<путь>" -Recurse -Force` и `git worktree prune`.

Шаг готов, когда у каждого пункта есть вердикт с фактом, а `git worktree list` показывает только рабочую копию.

### 6. Результат — сообщение 2

**Замечания** — сквозная нумерация, по убыванию P. В каждом: P, что не так, `файл:строка`, чем подтверждено (команда, цифры), предлагаешь ли комментарий.

| P | Когда |
|---|---|
| P0 | ломает прод, данные или сборку; мержить нельзя |
| P1 | основной сценарий не работает |
| P2 | баг во второстепенном сценарии, регрессия, доступность, хвосты |
| P3 | полировка, стиль, мелочи |

**Проверено, в порядке** — пункты, которые подтвердились, чтобы было видно покрытие.

**Прогоны** — `typecheck` / `lint` / `test` / `build` с результатом.

**Черновики** — `К<номер замечания>` и адрес: `файл:строка, новый тред` или `ответ в тред «<заголовок>»`. Текст — по разделу «Комментарий».

### 7. Доработать черновики

Пользователь правит по номерам («К1 мягче», «3 не пишем»). Присылай обновлённые черновики целиком.

### 8. Отправить — по команде «отправляй»

- Новый тред к строке: `POST .../discussions` с `position` (`position_type: text`, `base_sha`/`start_sha`/`head_sha` из свежих `diff_refs`, `old_path`, `new_path`, `new_line` для добавленной строки; для неизменённой — ещё `old_line`). Перед отправкой сверь, что `head_sha` совпадает с проверенным коммитом и строка на месте.
- Ответ в тред: `POST .../discussions/<id>/notes`. Тред был разрешён — верни его в нерешённые: `PUT .../discussions/<id>?resolved=false`.
- Больше в GitLab ничего не меняй: разрешение тредов, апрув, статус MR — за пользователем.

Готово, когда у каждого отправленного комментария в ответе API есть `id`, а у комментария к строке — `type: DiffNote` и верные путь и строка. Сообщи список: номер, адрес.

## Комментарий

Пишешь коллеге от имени пользователя.

- **Тон — рекомендательный**: «Кажется…», «Предлагаю поправить…», «Можно…», «Если была причина — напиши, пожалуйста». Указательный («Убери…») — только когда пользователь попросит.
- **Голос**: первое лицо, прошедшее время («собрал», «проверил»), на «ты». Без оценки P и без подписи.
- **Структура**:
  1. заголовок жирным — суть одной фразой в том же тоне;
  2. что не так и чем подтверждено: как воспроизвёл, цифры;
  3. предложение исправления, при необходимости — блок кода.
- Одно замечание — один комментарий.
- Неполное исправление по старому треду — ответ в этот тред; новая проблема — новый тред к строке.
