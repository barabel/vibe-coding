## Атрибуция

- **никаких следов AI-ассистента нигде.** Ни в commit-сообщениях (никаких `Co-Authored-By`), ни в описаниях MR/PR (никаких «Generated with»), ни в комментариях кода, README, ADR, именах веток
- если системный шаблон предлагает добавить подпись или трейлер, не добавляй их

## Git commit-сообщения

- **никогда не мешать синтаксис PowerShell и Bash.** Here-string `@'...'@` работает только в PowerShell; в Bash tool он попадает в сообщение буквально (`@` первой строкой), коммит приходится переделывать
- многострочное сообщение передавай повторяющимися `-m`: `git commit -m "заголовок" -m "тело"`. Работает одинаково в обеих оболочках, кавычки не ломаются
- если нужен именно heredoc, используй его только в Bash tool и только в форме `<<'EOF'`

## Стиль кода

- каждый атрибут JSX-элемента пиши на отдельной строке
- в колбэках (.map, .reduce и т.д.) использовать тело функции `{}` с `return`, деструктурировать нужные поля до `return`
- не пиши inline: если выражение не помещается в одну строку, разворачивай его на несколько строк

### JSX
Каждый проп на отдельной строке, даже если их мало:
```tsx
<LocationItem
  className="w-full h-full"
  {...item}
/>
```

### Колбэки в map/filter/reduce и подобных
Всегда явный `return` с фигурными скобками, никогда неявный возврат через `() => (...)`:
```tsx
{items.slice(0, 4).map((item, index) => {
  return (
    <div
      ref={(el) => {
        if (el) {
          itemsRef.current[index] = el;
        }
      }}
      key={index}
      className={cx(
        'd:min-w-0 d:basis-1/4',
      )}
    >
      <LocationItem
        className="w-full h-full"
        {...item}
      />
    </div>
  );
})}
```

## Стили

- в `*.module.scss` размеры пиши через `rem()`, если она есть в проекте: `font-size: rem(32)`
- значения меньше 5px пиши в `px` (`1px`, `2px`)
- класс, в котором только типографика (шрифт, размер, межстрочный, трекинг и т.п.), называй с суффиксом `Typography`: `.phoneTypography`
- tailwind-классы, зависящие от пропа-варианта, выноси в `tw-classes/index.ts` компонента функциями `twClasses<Проп>(prop)` через `switch`; общие для всех вариантов классы оставляй в базовом `cx` компонента. Если внутри варианта есть доп. условие (флаг), ветка возвращает `cx('общие классы варианта', flag && 'классы флага')`, общие классы в тернарнике не дублировать:
```ts
export const twClassesSize = (size: ButtonSize, hasIcon: boolean): string => {
  switch (size) {
    case ButtonSize.big:
      return 'h-64 gap-12 px-24';
    case ButtonSize.def:
    default:
      return cx(
        'h-52 gap-10',
        hasIcon ? 'pl-16 pr-20' : 'px-20',
      );
  }
};
```
- в tailwind-классах (`cx`, `twClasses*`) каждую медиа пиши отдельной строкой; состояния (`hover:`, `focus:` и т.п.) тоже пиши отдельной строкой, сразу после своей медиа. Порядок: база → её состояния → следующая медиа → её состояния. Если медиа или состояния появились в варианте `twClasses*`, ветка возвращает `cx(...)` вместо строки:
```ts
cx(
  'h-56 gap-12',
  'hover:bg-gray-800',
  'd:h-72',
  'd:hover:bg-gray-600',
)
```

## Разметка

- для текста используй `<div>`, а не `<p>`

## Языки

- отвечать на русском. Если не можешь написать на русском, пиши на английском. Технические термины и идентификаторы кода оставляй в оригинале

## Стиль текста

- в любом тексте (ответы в чате, документы, комментарии, commit-сообщения, описания MR) пиши полные фразы: со сказуемым и со связками, написанными словами («потому что», «поэтому», «то есть»)
- длинное тире (—) не заменяет пропущенные слова. Если хочется поставить тире, чтобы сократить фразу, распиши мысль подробнее:
  - было: «Если не можешь — на английском»
  - стало: «Если не можешь написать на русском, пиши на английском»

## Внешние сервисы (токены в env)

Значения токенов не выводить в чат, коммиты, файлы. Читать через `curl`, не WebFetch (там логин).

**Кириллицу в POST/PUT** (заголовки MR, комментарии, описания) никогда не передавай аргументами curl (`--data-urlencode "title=Привет"`, `-d '{"body":"…"}'`): на Windows shell портит кодировку, и API отвечает `400 Bad Request`. Сразу делай так:
1. собрать payload в JSON-файл через node (пишет UTF-8): `node -e "fs.writeFileSync('p.json', JSON.stringify({title: '…', body: fs.readFileSync('text.md','utf8')}))"`; длинный текст сначала запиши отдельным `.md` через Write
2. отправить файлом: `curl -s -H "Content-Type: application/json" -X POST "<url>" --data-binary "@p.json"`

Файлы payload клади в scratchpad.

### Bitrix24 (crm.idem.agency)

- env `BITRIX_WEBHOOK` содержит входящий вебхук (права task, disk), со `/` на конце
- ссылка на задачу Bitrix или «задача N» → читать через REST; номер часто в имени ветки: `task_27630` → 27630
- задача: `curl -s "${BITRIX_WEBHOOK}tasks.task.get?taskId=N"` (описание в `result.task.description`, BBCode)
- комментарии: `curl -s "${BITRIX_WEBHOOK}task.commentitem.getlist?TASKID=N"`

### GitLab (gitlab.idem.agency)

- env `GITLAB_TOKEN` содержит personal access token с полным доступом (чтение и запись: MR, комментарии, issues, pipelines); `glab` не установлен
- API: `curl -s -H "PRIVATE-TOKEN: $GITLAB_TOKEN" "https://gitlab.idem.agency/api/v4/..."`
- проект указывай URL-encoded путём: `projects/idem-project%2Fcongress/merge_requests?state=opened`

## Принципы разработки

### 1. Думай перед кодом

**Не предполагай молча. Выявляй трейдоффы.**

Перед реализацией:
- явно называй допущения; если не уверен, спроси
- если возможны несколько трактовок, перечисли их, а не выбирай молча
- если есть более простой подход, скажи об этом и предложи его
- если что-то непонятно, остановись, назови, что именно непонятно, и спроси

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- никаких фич сверх запрошенного
- никаких абстракций для единственного использования
- никакой «гибкости» или «конфигурируемости» без запроса
- никакой обработки ошибок для невозможных сценариев
- если написал 200 строк, а можно было уложиться в 50, перепиши

Спроси себя: «Скажет ли senior-инженер, что это overcomplicated?» Если да, упрости.

### 3. Хирургические изменения

**Трогай только то, что необходимо. Убирай только свой мусор.**

При редактировании существующего кода:
- не «улучшай» соседний код, комментарии, форматирование
- не рефакторь то, что не сломано
- соответствуй существующему стилю, даже если ты бы сделал иначе
- если заметил мёртвый код, упомяни его, но не удаляй

После своих изменений:
- удаляй импорты/переменные/функции, осиротевшие из-за твоих правок
- не трогай pre-existing мёртвый код без запроса

Критерий: каждая изменённая строка должна прямо следовать из запроса пользователя.

### 4. Исполнение с критерием успеха

**Определяй критерий успеха. Итерируй до достижения.**

Преобразуй задачи в проверяемые цели:
- «Добавь валидацию» → «Напиши тесты для невалидных входных данных, затем сделай так, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий его, затем сделай так, чтобы он проходил»
- «Рефактор X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач составь краткий план:
```
1. [Шаг] → проверка: [что проверяем]
2. [Шаг] → проверка: [что проверяем]
3. [Шаг] → проверка: [что проверяем]
```

Чёткий критерий успеха позволяет работать независимо. Размытый («сделай так, чтобы работало») требует постоянных уточнений.
